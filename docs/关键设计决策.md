## 关键设计决策（含历史问题修复记录）

### 1. 项目重心从"AI 编码 Agent"收回到"聊天体验"

项目最初的方向是做一个类似 Claude Code / Codex 的 AI 编码 Agent（当时的"Project 模式"）：文件读写、`apply_patch`、`run_command`、Git 集成、项目索引、写操作确认弹窗，一整套都做了。开发一段时间后发现，业余项目很难在"编码 Agent 效果"这条赛道上追平有专门团队长期投入的产品——上下文管理、代码理解深度、工具调用可靠性，这些问题的天花板很大程度上依赖持续的工程投入和底层模型能力，不是短期能补齐的。

于是把重心收回到项目真正有差异化的地方——"和企业聊天"这个角色扮演体验本身（`app/resources/full|lite/` 下的人格与台词文件是这部分真正的护城河）。Project 模式、写操作工具、双模式共享引擎的整套机制都已经移除，工具集收窄为 `read_file`/`list_directory` 两个只读工具。下面第 2～4 条记录的是移除前的历史设计，仅供理解代码演进过程参考，**当前代码里已经不存在**。

### 2.（历史）双模式共用一个 AgentEngine 实例

Chat 模式和 Project 模式曾经共享同一个 `AgentEngine` 实例，代价是一方发起新请求会通过 `start()` 内部的 `cancel()` 悄悄打断另一方正在跑的请求。当时的解法是两边发送前都检查 `engine->isBusy()`。

现在只有一个页面在用这个引擎，互斥抢占问题从架构上就不存在了，`isBusy()` 简化成了纯 `isRunning_`。

### 3.（历史）写操作确认机制，预览与执行必须用同一套逻辑

写操作（含 `run_command`）曾经不会立即执行：`ToolExecutor::previewDiff()` 生成预览 → `ConfirmDialogs` 弹窗展示 → 用户选择接受/拒绝。`apply_patch` 的预览和真正执行一度是两份独立实现，容易跑偏，后来统一成同一个 `applyPatchesToContent()`。

这一整套（`previewDiff`/`isBlacklistedCommand`/`ConfirmDialogs`/`writeConfirmationRequired`）随着写操作工具一起移除。现在只有只读工具，不存在需要用户确认的场景。

### 4.（历史）项目索引的缓存策略

首次打开项目全量扫描并缓存到 `.azur/project_index.json`；再次打开对比每个已收录文件的 `lastModified`。这部分逻辑在 `ProjectAnalyzer` 里，已随 Project 模式一起移除。

### 5. ConversationView — 消息展示组件

`ChatPageWidget` 现在是唯一持有 `ConversationView` 的地方。这个组件当初是为了消除 `ChatPageWidget` 和 `ProjectPage` 两边几乎一样的 `appendMessage()`/`onChunkReceived()`/流式节流/输入框控制逻辑（约 150 行重复代码）而抽出来的共享组件；`ProjectPage` 移除后它成了唯一调用方，但"只负责展示，不接触业务逻辑"的设计原则依然保留——发送按钮只管发信号，要不要真的调用 `AgentEngine` 由外层（`ChatPageWidget`）决定，方便以后再拆分调用方。

### 6. Prompt 资源的兜底路径必须和 qrc 别名对齐

`PromptLoader::loadFile()` 先尝试读取编译时写死的源码树路径（`RESOURCES_DIR`，开发时用），失败了会退到 `app.qrc` 打包进二进制的内容（分发后用）。这两条路径请求的是同一个相对文件名（例如 `full/enterprise_personality.md`），如果 `app.qrc` 里的 `<file alias="...">` 没有带上同样的 `full/`/`lite/` 前缀，qrc 兜底会静默失效——打包分发到别的机器后人格设定会直接丢失，且不会有任何弹窗提示，只有 `qWarning()` 写进日志。**改 `app.qrc` 或者改 `loadFile()` 的调用参数时，务必让两边路径保持一致**，可以用 `PromptLoader::buildChatSystemPrompt()` 在没有 `RESOURCES_DIR`（比如把整个源码树临时改名）的环境下跑一次来验证 qrc 兜底真的生效。

### 7. Python 工具后端：脚本还是服务

工具调用部分拆了一个 Python 实现（`python/azur_tools/`），走"脚本 + stdio JSON 协议"路线，而不是常驻服务进程。理由：

- **每次调用拉起一次子进程**（`QProcess` → `azur_agent/Scripts/python.exe cli.py`），成本在几十到几百毫秒量级，对"AI 回复时读个文件"这种低频场景完全可接受；换来的是零生命周期管理（不用管服务挂了/端口占用/状态同步），C++ 侧代码最简。
- **安全规则保持双端一致**：`executor.py` 是 `tool_executor.cpp` 的等价移植（同样的路径穿越防护、白名单、二进制/大小上限判断），C++ 侧 `resolveSafePath()` 的判断逻辑在 Python 里用 `os.path.realpath` + `relpath` 前缀判定复刻。两边互相对照，测试（C++ `test_python_backend.cpp` + Python `test_executor.py`）各自覆盖自己那一侧。
- **默认开启、坏了自动降级**：主程序 `main.cpp` 默认 `setUsePythonBackend(true)`；只有后端基础设施故障（找不到 venv / 进程起不来 / 超时 / 坏 JSON）才回退 C++ 原生实现并关掉开关，避免每次调用都白试。工具本身执行失败（如路径越界）不算故障，结果原样回传。
- **编码坑（已修）**：Windows 下 Python 写 stdout 默认用系统代码页（GBK），而 `json.dumps(ensure_ascii=False)` 里的中文会被编成 GBK 字节，C++ 侧 `QJsonDocument` 按 UTF-8 解析直接失败——表现为"后端返回了无法解析的响应"。修法是在 `cli.py` 顶部强制 `sys.stdin/stdout.reconfigure(encoding="utf-8")`。

### 8. P1 语气一致性：post-history instructions 放在"历史之后、生成之前"

对话一长，企业容易崩人设、语气漂移。Character Card V2 的 `post_history_instructions` 思路是：把一段语气约束放在**离生成点最近**的位置（所有对话历史之后、模型开始生成之前），这是对语气影响最大的杠杆点。现有人格文件（`full/enterprise_personality.md` 等）已经写得很完善，不需要重写内容，只需新增 `full/enterprise_instructions.md` / `lite/enterprise_instructions.md` 这两段"生成前语气约束"，并在注入时保证和旧版行为兼容：

- `PromptLoader::buildPostHistoryInstructions(style)` 单独加载指令文件，和 `buildChatSystemPrompt()` 分开——两者角色不同（一个开头、一个历史之后），混在一起会导致注入位置没法单独控制。
- `AgentEngine::sendRequest()` 组装完消息列表后注入：**云端模型**追加一条尾部 `{role:"system"}`；**本地模型**（Ollama 等不支持多 system 的）拼到最后一条 user 消息内容后，用 `\n\n---\n\n` 分隔。
- 指令为空时跳过注入，行为与旧版完全一致——这是**默认参数设计**换来的：`start()` 的第 8 个参数带默认值 `QString()`，所有旧调用点零改动。
- `ToolExecutor::pythonInterpreterPath()` / `toolCliPath()` 从 private 改成 public，是为了让 `TtsClient` 复用同一套"从可执行文件目录向上回溯"定位虚拟环境和脚本的逻辑，避免复制一份。

### 9. P2 语音朗读：复用"脚本 + stdio JSON 协议"通道，而不是新增服务

语音合成没有新起架构，直接复用 Python 工具后端验证过的通道：

- 新增 `python/azur_tools/tts_cli.py`，和 `cli.py` 完全同款 stdin/stdout JSON 协议（`sys.stdin/stdout.reconfigure(encoding="utf-8")` 防 GBK 坑），请求 `{"text","voice","output"}`、响应 `{"ok","content"}`。这样 C++ 侧只需要一个简单的 QProcess 封装（`core/ttsclient`），不用为 TTS 单独设计一套交互协议。
- 选 edge-tts 而不是本地 TTS：企业是中文女声，edge-tts 的中文音色质量好且零训练成本；代价是 GPL-3.0 和运行时需联网。对"聊天气氛音"这种非关键路径，合成失败只 `qWarning` 不打扰用户，是可接受的降级。
- TTS 走 QProcess **纯异步**（信号槽 + 30s 超时 kill，不用 `waitForFinished`），因为它是 UI 线程的一部分——阻塞会直接卡死聊天界面。这和 `ToolExecutor` 的 Python 后端不同：工具调用本来就在 Agent 请求循环里，超时后模型会收到工具错误；TTS 没有请求循环兜底，所以必须自己防超时。
- 播放用 Qt Multimedia（`QMediaPlayer` + `QAudioOutput`），只接在 `MainWindow`，`ttsclient` 本身只做 QProcess 不依赖 Multimedia，因此测试目标不用链接 Multimedia 模块。
